# Ассистент менеджера проекта: еженедельный статус-отчёт

Что автоматизировано: сбор статус-отчёта по данным GitHub (коммиты, PR, задачи,
запуски CI). Раньше его собирали вручную из истории репозитория и доски.

## Как устроено

- `tools/pm_report.py` через GitHub API берёт данные за период и **сам считает все числа**.
- Модель (Groq, `openai/gpt-oss-20b`, температура 0, seed 42) получает только готовые факты и
  формулирует три раздела: итоги, риски и зависшее, что сделать дальше. Оценивать сроки и
  прогнозировать ей запрещено промптом.
- Скрипт проверяет, что каждое число в тексте модели есть среди фактов, и выводит все числа,
  которых там нет. Проверка грубая: она ловит выдуманные числа, но не ловит перепутанные
  местами. Поэтому отчёт перед отправкой проверяет человек.
- Если Groq недоступен или ключа нет, отчёт всё равно создаётся, но только с числами.
- Версия промпта: `pm_report_v1` (константа `PROMPT_VERSION`). Меняется вместе с текстом промпта.

## Запуск

Автоматически: каждый понедельник в 09:00 по Астане (workflow `PM weekly report`).
Вручную: Actions → PM weekly report → Run workflow; поля `since` и `until` задают период
(например, один спринт). Результат: сводка на странице прогона и артефакт `pm-report-<id>`
с файлами `.md` и `.json` (факты, ответ модели, параметры, список непроверенных чисел).

Локально:

```bash
python tools/pm_report.py --repo madyokkaa/TableFlow --since 2026-11-01 --until 2026-11-14
```

Нужны `GITHUB_TOKEN` (в Actions выдаётся сам) и `GROQ_API_KEY` (секрет репозитория; без него
отчёт без текста модели).

## Что нельзя передавать модели

- персональные данные гостей: имена, телефоны, email, тексты броней и сообщений бота;
- ключи, токены, пароли и любое содержимое `.env`;
- код и данные заказчика, не опубликованные в репозитории;
- переписку с заказчиком и персоналом.

В модель уходят только числа и заголовки задач из публичного репозитория. Заголовки задач
не должны содержать персональных данных; если содержат, отчёт не публикуют.

## Шаблон промпта

См. `SYSTEM` в `tools/pm_report.py`. Структура: роль, входные данные (`FACTS`), формат вывода
(три раздела), ограничения (только числа из фактов, без прогнозов), поведение при нехватке данных.

## Проверка отчёта человеком

1. Сверить каждое число в таблице фактов с GitHub (коммиты, PR, задачи, Actions).
2. Прочитать текст модели и сверить каждое утверждение с фактами.
3. Записать найденные неточности в журнал: что написано, что на самом деле, тип ошибки
   (число, название, вывод, лишнее), как найдена.
4. Засечь время проверки.
